# ADR-0007: 퍼널 단계 정의와 이벤트 수집

- 상태: 채택
- 날짜: 2026-09-16

## 맥락
초기 구현은 「방문 → 신청」 두 단계만 있었다. 이 시스템의 목적은 마케팅 채널별 퍼널 추적이므로, 운영자는 "어디서 새는지"를 단계별로 봐야 한다. 특히 봇·즉시 이탈과 실제 사람의 이탈, 작성 중 포기와 제출 실패는 다른 조치가 필요하다.

## 결정
### 1. 다섯 단계 + 실패
| 단계 | 이벤트 | 기록 주체 | 수집 시점 |
|---|---|---|---|
| 링크 클릭 | `VIEW` | forms 서버 | `GET /l/:code`, `/f/:slug` 200 응답 |
| 폼 도달 | `FORM_VIEW` | 주입 스크립트 | 스크립트 실행 + `<form>` 발견 |
| 작성 시작 | `FORM_START` | 주입 스크립트 | 첫 `input`/`change`/`focusin` (필드명 meta) |
| 제출 시도 | `SUBMIT_ATTEMPT` | 주입 스크립트 | `submit` 이벤트 (브라우저 필수값 검증 통과 후) |
| 신청 완료 | `SUBMIT_SUCCESS` | forms 서버 | `POST /f/:slug/submissions` 201 (신청 저장과 한 트랜잭션) |
| 실패 | `SUBMIT_ERROR` | 주입 스크립트 | 응답 ≠ 2xx(`status`) 또는 fetch 실패(`network`) |

- `VIEW`·`SUBMIT_SUCCESS` 는 서버만 기록한다. 클라이언트가 보낼 수 있는 타입은 4종으로 제한(400).
- 브라우저 이벤트는 `navigator.sendBeacon` 으로 `POST /f/:slug/events` (같은 origin → CSP 변경 없음). 방문자 쿠키가 없으면 204 로 받되 기록하지 않는다.

### 2. 저장
- 기존 `visits` 테이블을 범용 `events` 로 교체. 마이그레이션에서 `visits → VIEW`, `submissions(visitorId 있음) → SUBMIT_SUCCESS` 로 이관.
- `submissions` 는 CRM 명단으로 그대로 유지. 퍼널의 신청 수는 `SUBMIT_SUCCESS` 이벤트(방문자 쿠키 필요) 기준이므로 쿠키 없이 제출된 건은 명단에는 있지만 퍼널에는 없다 — 대시보드 "신청" 과 CRM 명단 건수가 다를 수 있음을 문서화.

### 3. 지표
- 단계 수 = 해당 타입을 1회 이상 낸 **고유 방문자**(`gu_vid`) 수. 페이지뷰(이벤트 수)는 보조.
- 단계 전환율 = 이번 단계 ÷ 직전 단계, 누적 전환율 = 단계 ÷ 링크 클릭, 전체 전환율 = 신청 완료 ÷ 링크 클릭.
- 이탈 = 직전 − 이번. 최대 이탈 구간 하나만 화면에 색으로 표시한다.
- 채널 귀속 = 이벤트가 발생한 페이지의 링크 코드(**마지막 클릭**). 링크 삭제 시 `linkId=null` 로 보존.
- 기간 = 이벤트 시각, KST 자정 정렬. `today/7d/30d/90d/all/custom`. 비교 = 같은 길이의 직전 구간.
- 봇 의심 = `VIEW` 는 있지만 `FORM_VIEW` 가 없는 방문자(스크립트 미실행).
- 여정 정렬 = `createdAt`, 동률이면 단계 순 (비콘이 제출 응답 뒤에 도착할 수 있음).

### 4. 집계 방식
요청 시 `events` 를 운영자·필터·기간으로 자른 CTE 위에서 `COUNT(DISTINCT visitorId) GROUP BY type[, key]`. 규모가 커지면 일별 롤업 테이블로 전환.

## 대안
- 단계를 3개(클릭·작성·신청)로: 봇/즉시 이탈과 실제 이탈을 구분 못 한다.
- 페이지뷰 기준 전환율: 재방문이 많은 채널이 불리하게 보인다. 방문자 기준을 택했다.
- 첫 클릭 귀속: 리마케팅 분석에는 유용하지만 채널 예산 판단에는 마지막 클릭이 직관적. 토글은 후순위.

## 결과
대시보드(5단계 카드·퍼널·추이·채널 비교), 캠페인 상세(링크별·폼 A/B·히트맵·실패·품질), CRM 명단 여정(신청/미신청)이 모두 같은 필터로 동작한다.
